# Rev-Pi-Farm-Control-System

Farm control system running on Revolution Pi Connect 4 units.

## Layout

- `API/` - hardware API, the layer between the RevPi I/O and the controllers
  - Include roots are `-IAPI/include -IAPI/src`; `API/include` headers are included by bare name (`"devices.h"`), cross-folder `API/src` includes are written relative to `API/src` (e.g. `"HAL/electronics.h"`), same-folder includes use the bare name
  - `API/include/` - what external programs (e.g. the controller) include from the API
    - `devices.h` - public device interface: abstract base classes `pump`, `float_switch`, `valve`, `pressure_transducer`, `tds_sensor`, `flow_sensor`, `level_sensor`, `conductivity_sensor` (uS/cm), `temperature_sensor` (deg F), `switched_load` (on/off only: lights, heater), `soil_sensor` (per-depth vectors), `toggle_switch` (`readValue`, 1 DI; local class `local_switch`), `toggle_switch_double_pole` (`readPole1`/`readPole2`, 2 DIs), `push_button` (`readPressTotal`: raw counter, reads don't change it, served by device_server; `readPushButtonCount`: non-virtual in the base, presses since that object's previous call, so each machine counts on its own; PULSE_IN on a counter-mode pin, first read false) (pure virtual, no hardware includes). Controller code uses only these, so local and remote devices are interchangeable
    - `config.h` - shared by every machine: every farm device as an `extern` base-class reference (`extern pump& feed_pump;`), `attachAllInterfaces()`. Includes only `devices.h`
  - `API/src/config/config_<name>.cpp` - one per machine, exactly one is built (`cmake -DDEVICE_CONFIG=<name>`, no default). The wiring: `electrical_interface`s and `local_*`/`remote_*` devices (anonymous namespace), bound to the references declared in config.h. A config only binds the devices that machine uses; a program using an unbound device fails to link
    - `config_test` - test bench RevPi (192.168.1.20), example devices. Same RevPi as `config_ro`; shares the names `feed_pump`, `inlet_valve`, `permeate_flow`
    - `config_ro` - RO RevPi (192.168.1.20), written from the CSV: 3 flow, 8 float (`feed_tank_high_float` removed 2026-11-11), 1 level (`feed_tank_water_level`, AIO `InputValue_3_i09`, 4-20 mA, 0-11.5, same sensor as the upper tank), 11 pressure, 2 conductivity, 1 temperature, 6 pumps (feed/RO pump = run relay + VFD alarm; RO pump speed = AIO pos 32 `OutputValue_1`, 4-20 mA, `Output1Range` = 9), 2 switched loads, 7 valves on the RS485 relays, 2 toggle switches (`repressure_toggle_switch` `I_4_i03`, `ro_toggle_switch` `I_5_i03`), plus every upper tank device bound remote (`upper_tank_high_float`, `upper_tank_water_level`, `irrigation_pump`, `well_4_pump`; needs 47100 open there to .20) (bound for user space; served only by their owner, the upper tank); serves its own devices and the WiseConn devices; no web UI
    - `config_uppertank` - upper tank RevPi (192.168.1.21, MIO + AIO + RO relay module): `upper_tank_high_float` (MIO `DigitalInput_4`), `upper_tank_water_level` (AIO `InputValue_1`, 4-20 mA), `irrigation_pump` (pressure setpoint only: AIO `OutputValue_1`, 0-10 V = 0-100 psi; no run relay, speed or alarm), `well_4_pump` (on/off only: RevPi RO relay module `RelayOutput_4`); also binds all 43 RO RevPi devices remote on `ro_revpi` (link to .20, shared with `ro_config_uppertank`) for user space (served only by their owner; needs 47100 on the RO RevPi open to .21); serves its own devices and the WiseConn devices
    - `client_config.cpp` (not a DEVICE_CONFIG; 2026-11-12) - the client config for `farm_client` (the console): every config.h device remote on a connection to its owner, addresses from `API/api.cmake` (`FARM_RO_HOST`/`FARM_UPPER_HOST`: 127.0.0.1 for this machine's own RevPi so its console works with the network down, the LAN address for the other; `FARM_CLIENT_LOCAL_*`), WiseConn as `remote_irrigation`/`remote_soil_sensor` from this machine's main (127.0.0.1, sharing the RevPi link when local); serves nothing. Generated from config_host_pc's list: keep the two in step
    - `config_host_pc` - Ubuntu dev PC / emerald-server, all RevPi devices remote; `addLocalDevices` serves only the WiseConn devices (for the local console, on `main_host_pc`'s loopback server)
  - `API/hardware_setup.csv` - user's device list (name, id, host IP, interface type, pin, analog range); configs are written by hand from it
  - `API/src/HAL/` - hardware abstraction layer
    - `electronics.h/.cpp` - `electrical_interface`: one I/O point bound to a PiCtory variable
    - `analog_input.h/.cpp` - shared 4-20 mA / 0-10 V scaling for pressure and TDS; < 3.5 mA = broken wire
    - `piControl.h` - vendored KUNBUS driver header (MIT), do not edit
  - `API/src/devices/local_devices/local_*.h/.cpp` - devices wired to this RevPi, each inherits its base from `devices.h`
    - `local_pump(speed, on_off, alarm, pressure, pressure_min = 0, pressure_max = 1)`: non-owning pointers to the interfaces; nullptr = not fitted. Speed 0-1 (hard-coded) and pressure pressure_min..pressure_max (rejected outside) map to 0-10 V, 4-20 mA or 0-100 % PWM
    - `local_float_switch`, `local_valve`, `local_pressure_transducer`, `local_tds_sensor`, `local_flow_sensor`, `local_level_sensor`, `local_conductivity_sensor`, `local_temperature_sensor`, `local_switched_load` - one interface each; reads return false on failure and fill an out param
  - `API/src/devices/remote_devices/` - devices owned by another RevPi on the LAN. One owner per device
    - `remote_link` (lives in `comms/src/`) - one TCP connection per remote RevPi (port 47100), shared by its `remote_*` devices; an io thread connects (1 s backoff, 1 s connect timeout) and polls `snapshot` every 0.5 s into a cache (also keeps the owner from idling the connection out). Reads (`query*`) answer from the cache instantly, never touching the network: fail if the value is older than 3 s (`STALE_TIMEOUT`, a stall) or the owner couldn't read it; the cache is cleared when the link drops, so reads fail at once after an owner restart; in the first 2 s after the link is created reads wait for the first snapshot. Commands are queued on the same socket and wait up to 1.5 s for their own reply (late replies are discarded in order), fail at once while disconnected or with 16 requests outstanding, and trigger an immediate snapshot on success. The link is only dropped after 25 s with requests outstanding and nothing received (longer than the owner's 20 s idle timeout). Timings: `link_timing` in `comms/src/protocol.h`. Rework 2026-11-11 (was synchronous request/reply with 300 ms timeouts, which caused random read failures and lag over HaLow)
    - `remote_*` - one proxy per base class, `(remote_link&, device_name)`; network failure returns false (`readAlarm` returns true). Includes `remote_soil_sensor` and `remote_irrigation` (2026-11-12; `scheduleIrrigation` goes to the owner's device, so on a WiseConn zone it starts a real irrigation)
    - `device_server` - on the owner; a `line_handler` registered on main's `line_server` (`comms/`), so requests are only handled inside `server.poll()` and never race local control code. No watchdog (removed 2026-11-11): commands hold after the client disconnects or goes silent (manual control is a precaution; the old reset could close a valve a running RO state needed)
    - Protocol: text lines `"<device> <method> [arg]"` -> `"ok [value]"` / `"fail"` / `"err <reason>"`; method names = C++ method names. Soil per-depth values as `a,b,c`; `scheduleIrrigation` arg `HH:MM-HH:MM` (today) or minutes (from now). `device_server` serves any config.h device (local, remote or WiseConn) and refuses nothing. `"snapshot"` -> `"ok <name>.<method>=<value>;<name>.<method>;..."` (no `=` = failed read): every `line_handler::snapshot()` (`device_server`: every read method of every device, via its own `handleRequest`; `ro_server`: `ro.readState`, `ro.isSettling`). Names can't contain `.`, `;`, `=`; `ping` and `snapshot` are reserved. `line_server` queues replies per client (`tx_buffer`, POLLOUT) so big snapshots go out in pieces. No authentication: restrict the firewall to the other RevPi
  - `config.h` also exposes `addLocalDevices(line_server&)` (forward-declared `line_server`); each config registers its local devices on its `device_server devices` under their public names (snake_case of the CSV name), then `devices.registerWith(server)`
  - `API/src/devices/wiseconn_devices/` - devices read from the WiseConn cloud API (farm irrigation system), in `farm` (libfarm.a) on every config since 2026-11-12 (to be replaced by more RevPis eventually; every machine's user space gets the same access): bound once for all configs in `API/src/config/wiseconn_farm_devices.cpp` (built next to the chosen `config_<name>.cpp`; every config's `addLocalDevices` serves them through `addWiseconnDevices(device_server&)` (`wiseconn_farm_devices.h`), so their commands, `scheduleIrrigation` included, are open on that machine's port 47100 like any device's; `main_host_pc` runs no `line_server` yet; it sets the process `TZ` to the keys' `time_zone` before creating the link, so it works on the UTC RevPis; nothing else uses local time, the scheduler uses system_clock time points); `ro_console` reads them through the local service (`remote_irrigation`/`remote_soil_sensor`). Only `farm` sees `wiseconn_keys_text.h`. `main_ro`/`main_uppertank` never read them, so an internet outage changes no control. Read only, GET requests only: the WiseConn valves are live, never send anything that changes them. Bound (every config): soil probes `zone_7_soil`, `zone_8_soil`, `zone_10_3_soil` (3 depths 4/8/12 in; moisture %, ETC = EC in raw VIC units, temperature deg F) 7 flow meters (`flow_sensor`, `wiseconn_flow_sensor`, gal/min, 2026-11-12: `main_flow`, `city_water_flow`, `well_1_flow`..`well_5_flow`; `[flows]` = `name = zone id, measure id`, read from the zone's measures poll every 60 s, WiseConn updates ~5 min; Well #2 has sent nothing since 2026-09-04 so it reads `---`; shown in the console's "Flow meters (WiseConn)" tile on Main-Dashboard) and 24 irrigation zones (`irrigation`: `valve_1_1`..`valve_10_3`, `overhead_1`..`overhead_6`, `city_water_fill_valve`; zone ids in `[irrigations]`): `readOn` from `GET /farms/3995/hydraulics` (zone's valve `Operating` = on, `Off`; running valves say `Operating`, not `On`, fixed 2026-11-11; the valve list is polled every `hydraulics_poll_seconds` (default 10 s, soil measures every `poll_seconds` = 60 s), stale after 1 min of failed polls); `scheduleIrrigation(sh, sm, eh, em)` (today) sends `POST /irrigations {zoneId, initTime, endTime, directSchedule: true}` (farm local times, no Z) and `scheduleIrrigation(minutes)` sends `{zoneId, duration}`; both START REAL IRRIGATIONS, block ~1 s, never retry; a success adds the new irrigation's id (from the POST reply, an array) to the zone's list (every booking from here, lost on a restart), `readScheduledIrrigation(int&)` returns the latest and `cancelIrrigation()` sends `DELETE /irrigations/<id>` for every id in the list, removing the deleted ones and keeping refused ones for the next cancel (WiseConn only deletes a future, not-yet-sent one; deleting is asynchronous: the reply is "The irrigation is being deleted" and `GET /zones/<id>/irrigations?initTime=YYYY-MM-DD&endTime=...` keeps listing it with `deleting: true, actionInProgress: "Removing"` for a few minutes (seen 2026-11-12 on the sooner of two bookings; the later one went at once); 2026-11-12; device_server `readScheduledIrrigation` (snapshot) / `cancelIrrigation`, `remote_irrigation` reads the id as text since it doesn't fit a float). Base URL `https://api.wiseconn.com` (default and in the keys file since 2026-11-12): the `/irrigations` endpoints return HTTP 500 on `apiv2.wiseconn.com`, which is why the one earlier schedule attempt failed; `GET /farms/<id>/realIrrigations?initTime=YYYY-MM-DD&endTime=...` gives past irrigations. Never test them against the real API without the user choosing the zone and time; test against a fake local server via `base_url`. Web UI shows on/off plus start/end time boxes and a Schedule button (browser confirm, then `<zone> scheduleIrrigation HH:MM-HH:MM` to `/api/command`; starts a real irrigation)
    - `wiseconn_link`: background thread polls `GET /zones/<id>/measures` every 60 s with the `curl` program, caches values; reads are instant, fail when `lastDataDate` is older than 45 min
    - Keys: `wiseconn_keys.txt` (repo root, git-ignored: api_key, farm_id 3995, time_zone, zone and measure ids), built in as text by CMake into `build/generated/wiseconn/`; missing = devices off. Copies on emerald-server, the dev PC and the RO RevPi (2026-11-12); the upper tank RevPi needs one too (copy it there before building, or its WiseConn reads fail)
    - Gotcha: WiseConn `lastDataDate` ends in Z but is farm local time (America/Los_Angeles); parsed as local time; `wiseconn_farm_devices.cpp` and `ro_console` set the process `TZ` from the keys' `time_zone`, so it works on the RevPis (UTC)
    - Details and how to find ids: `API/src/devices/README.md`
  - Output readback: `pump::readOn/readSpeed/readPressure`, `valve::readOpen` read the output process image as last written (not run/position feedback)
- `comms/src/` - line protocol between machines, independent of the API (`comms` library, `farm` links it). `protocol.h` (port 47100), `line_server` (one per machine, owned by `main_*`; `loopback_only` ctor flag listens on 127.0.0.1 only, default all interfaces; `allowOnly({addresses})` closes any connection from another address as soon as it's accepted (main_host_pc: 127.0.0.1, .20, .21, since emerald has no firewall); routes each request by its first word to the `line_handler` that registered it, names unique across handlers, single threaded `poll()`, drops a client idle 20 s (`idle_timeout_ms`), which changes nothing on the hardware), `remote_link` (client). Lets other modules (e.g. a future RO controller) share port 47100 with the device server
- `RO/` - RO controller (state machine over the config.h devices), outside the API. `RO/include/`: `types.h` (`RO_state`, `ALL_RO_STATES`, `toString`/`fromString`, `range`, `valve_state`/`pump_state`/`pressure_state<T>`/`flow_state<T>`, `valvesFor`/`pumpsFor`/`pressuresFor`/`flowsFor`, `VALVE_SETTLE_MS` = 10 s, `PUMP_STOP_MS` = 5 s (placeholder; both `#ifndef`, `-D` overrides); `procedure_types` moved to procedure.h), `ro_config.h` (like config.h: one header for every machine, implemented per machine in `RO/src/config/ro_config_<DEVICE_CONFIG>.cpp`; `addRO(line_server&, scheduler&)`, `updateRO()`, `setROState`, `readROState`, `readROSettling`, `setROSpeed`; no procedure functions since 2026-11-12 (the RO procedures are `procedure_config.h`'s `ro_procedure`, owned by `main_ro`); `addRO` registers `ro_server` on the RO RevPi only, elsewhere it returns true; its `scheduler&` parameter is unused, kept so `tests/` still build). `ro_config_ro`: the controller runs here (`ro`/`ro_server` are function-local statics so they're destroyed before config_ro's devices; using them before `addRO` aborts); `addRO` drives OFF at startup and registers "ro", `updateRO` every loop pass. `ro_config_host_pc` and `ro_config_uppertank` (added 2026-11-12, same code): the same functions go to the RO RevPi through `remote_ro` on the `ro_revpi` link defined (outside the anonymous namespace) in `config_host_pc.cpp` / `config_uppertank.cpp` (`extern`), so devices and RO share one connection and one snapshot poll; `addRO`/`updateRO` return true (`main_uppertank` doesn't call them or use the RO yet). The upper tank's link needs port 47100 on the RO RevPi open to 192.168.1.21 (opened 2026-11-12). `config_test` has no RO config. `RO/src/`: `ro` (non-blocking `setState` in phases, all timing in `ro`: 1. stop the pumps the new state has off; 2. if one of them was running (or its output can't be read), `update()` waits `PUMP_STOP_MS` for spin-down before touching valves (a pump still spinning down from an earlier setState keeps holding them); 3. open then close valves; 4. pumps start in `update()` after `VALVE_SETTLE_MS` (none if a valve failed); `isSettling()` = phase 2 or 4; pumps that stay on across a change keep running while the valves move; `~ro` does the same phases blocking (sleeps `PUMP_STOP_MS` if a pump was running); `ro()` (no scheduler and no procedure since 2026-11-12: the class knows nothing about procedures); `setHeaterState()` (called in `setState`) only sets the private `heater_active_` = `HeaterFor(state)` (types.h); `ro` never switches `cip_heater`, the heater is operated elsewhere), `ro_server` (`line_handler` built on the `ro_config.h` functions, not the `ro` object (2026-11-12), registered by `addRO` on the RO RevPi only; registers "ro": `setState <STATE>`, `readState`, `isSettling`, `setRoSpeed <0-1>` (snapshot `ro.readState`, `ro.isSettling`; a failed read answers `fail`; "ro_procedure" is `main_ro`'s `procedure_server`); the RO keeps its state when a client disconnects; `main_uppertank` and `main_host_pc` call `addRO`/`updateRO` too, which do nothing there), `remote_ro` (client). `ro_server` and `remote_ro` live in `RO/src/remote_ro/` (included as `"remote_ro/ro_server.h"`). CMake: library `ro` (RO/ro.cmake, machine specific: this config's RO config, `ro_server`, `remote_ro`, `ro.cpp` for the ro config only, so no second controller can run; links only `farm`, `comms`), linked into every program
- `procedure/` - farm procedures, outside the API and RO (`include/procedure.h`, `src/procedure.cpp`; libraries `procedure` / `procedure_client` (procedure/procedure.cmake, machine specific), include dirs `procedure/include`, `procedure/src`). Remote control, in `procedure/src/remote_procedure/` (included as `"remote_procedure/..."`): `procedure_control` (in procedure.h, 2026-11-12: abstract `run`/`stop`/`readProcedure(running, p)`, implemented by `procedure` and `remote_procedure`, like the device base classes); `procedure_config.h` (like config.h: every instance as `extern procedure_control&`, plus `addLocalProcedures(line_server&)`; one config per machine in `procedure/src/config/procedure_config_<DEVICE_CONFIG>.cpp` (ro, host_pc, uppertank) and `procedure_client_config.cpp` (console), laid out like the API configs: the instances this machine owns are plain `procedure` globals on main's global `sched` (`extern scheduler sched;`) with a `procedure_server` each, bound to the header's references, and `addLocalProcedures` registers them; elsewhere `remote_procedure` on `extern remote_link ro_revpi` and `addLocalProcedures` returns true. Instances: `ro_procedure` (owned by the RO RevPi, served as "ro_procedure") `repressure_procedure` (2026-11-12, REPRESSURE_CONTROL: the repressure pump tasks; owned by the RO RevPi, `procedure_config_ro.cpp`, user-stop action `repressure_pump.setOff()`, served as "repressure_procedure", started by `main_ro` at startup; remote on `ro_revpi` in the other configs) and three WiseConn procedures, one per set of valves (2026-11-12; owned by emerald-server: `procedure_config_host_pc.cpp` creates them on `main_host_pc`'s `sched`, each served under its own name; each user-stop action cancels what its own valves still have booked (`readScheduledIrrigation` then `cancelIrrigation`, which deletes every booking the zone made; zones with none skipped; only while WiseConn still allows deleting them)): `overhead_pattern_procedure` (`overhead_1`..`overhead_6`, OVERHEAD_PATTERN_1; was `irrigation_procedure`), `irrigation_pattern_procedure` (`valve_1_1`..`valve_10_3`) and `city_fill_valve_procedure` (`city_water_fill_valve`) (no procedure types of their own yet); the RevPi configs bind them remote on `remote_link host_pc("192.168.1.194")` and the client config on `FARM_HOST_PC_HOST` (127.0.0.1 in the host_pc build, else 192.168.1.194, set by procedure.cmake). `main_host_pc` listens on all interfaces but `allowOnly`s 127.0.0.1, .20 and .21 (2026-11-12), so the RevPis reach it). Changing the RO state mid-cycle doesn't stop it. Step times are `#define`s in procedure.h (`-D` overrides, CIP times are placeholders). `type()` = the one last started (for `readProcedure`)
- `scheduler/` - `scheduler` (`include/scheduler.h`, `src/scheduler.cpp`), independent of the API, CMake lib `scheduler` (every config, linked into every `main_*`). One instance per machine, owned by `main_*` (a global, so it outlives the `ro` static), which calls `sched.update()` every loop pass and passes it to `addRO`; `ro` and `procedure` only hold references. ## electrical_interface

- Interface types: `electrical_interface_type` enum + matching structs + `interface_value` variant, all in the same order (static_assert checks the count)
- Pins are PiCtory variable names, e.g. `I_1`, `O_1`, `Counter_1`, `PWM_1`, `InputValue_1`, `OutputValue_1`, `Output_Bit_1`
- `attach()` resolves the name and rejects a size mismatch; `getHardwareState()` / `setHardwareState()` return false on failure; set is refused for input types
- Process image types: DIO bits = 1 bit, DIO `Counter_N` = uint32, DIO `PWM_N` = uint8 0-100, AIO `InputValue`/`OutputValue` = int16 (mV / uA)
- Analog struct values are in V / mA; conversion assumes PiCtory AIO multiplier = divisor = 1
- DIO PWM frequency is per module, not per channel

## Device behaviour and PiCtory setup still needed

- Polarity (add an "inverted" option if wiring differs): float input on = `readSubmerged` true = submerged (confirmed 2026-11-03), off/false = dry; valve output on = open (normally closed valve); pump alarm input on = alarm (a normally-closed Danfoss alarm relay would need inverting)
- `local_pump::readAlarm()` is fail-safe: false if no alarm fitted, true if the alarm input can't be read or is the wrong type
- `setSpeed()` rejects values outside 0-1 (no clamping); analog reads are not clamped, so unwired 0-10 V inputs can read slightly negative (e.g. -0.2 ppm)
- Flow: `flow_sensor::update()` (virtual, no-op in the base and remote) must be called every main loop pass by the owner (`main_ro` calls it for `permeate_flow`, `concentrate_flow`, `feed_flow` at the top of its loop). `local_flow_sensor::update()` stores a (time, count) sample (at most one per 10 ms) and computes a rolling average from the newest sample at least `window` old (ctor arg, default 1 s). `readFlow()` only returns that value, so readers never affect each other; it fails for the first window after startup or a counter reset, if the last update couldn't read the input, or if `update()` hasn't run for 3 windows. Programs that own a flow sensor without `main_ro`'s loop (e.g. `tests/ro_*_test`) must call `update()` themselves
- PiCtory, before real use: DIO inputs for flow sensors must be in counter mode (`InputMode_N`); AIO input ranges must match each sensor (all currently ±10 V); AIO output ranges must be set for VFD speed (currently 0 = off)
- RO RevPi (192.168.1.20, hostname RevPi212936): DIO pos 31 = unsuffixed `I_N` (floats `I_2..9`, `I_1` unused since the feed tank high float was removed, VFD alarms `I_10..11`), DIO pos 30 = `_i03` (flow counters `Counter_1..3_i03`, already `InputMode` = 1 counter). On 2026-10-31 floats `I_1..5,8,9` read on (submerged), `I_6,7` off (dry); polarity on = submerged confirmed 2026-11-03

## Remote devices (two RevPis)

- Setup on each RevPi before they can talk:
  1. Open port 47100 only to the other RevPi (the protocol has no authentication):
     `sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="<other RevPi IP>" port port="47100" protocol="tcp" accept'`
     then `sudo firewall-cmd --reload`
  2. Build with `-pthread` (remote_link runs an io thread)
- Main loop on each RevPi:
  ```cpp
  attachAllInterfaces();
  line_server server;              // comms/src/line_server.h, port 47100, drops clients idle 20 s
  addLocalDevices(server);
  server.start();
  while (true) {
      // control logic
      server.poll(20);             // handles remote requests, doubles as the loop sleep
  }
  ```
- Using a device owned by the other RevPi, in that machine's config:
  ```cpp
  remote_link revpi_b("192.168.1.117");
  remote_pump remote_transfer_pump(revpi_b, "transfer_pump");   // name the owner registered in its device_server
  pump& transfer_pump = remote_transfer_pump;
  ```
  Device names must match on both RevPis (no discovery yet)
- Several readers of one flow sensor (local code, other RevPis, the console) all get the owner's 1 s rolling average; reads don't change it
- Remote cost: reads are cache lookups (microseconds); commands one round trip (~1 ms LAN, more over HaLow). Owner unreachable: commands fail at once, reads fail at once after a disconnect or after 3 s of a stall. RO RevPi snapshot ~3 KB, ~6 KB/s per polling client. Mixed versions: an old owner answers `snapshot` with `err unknown device`, so a new client reads nothing from it; deploy owners (upper tank, RO RevPi) before emerald-server
- Tested: 25/25 end-to-end on the PC (owner in a separate process, fake hardware); on the RevPi with real hardware over loopback (relay 1 switched remotely). Between two physical RevPis: in use since 2026-11-09 (`main_ro` reads `upper_tank_high_float` from the upper tank RevPi for the repressure tasks)
- Gotcha fixed once: don't pass a value and the call that fills it in the same expression (`f(read(x), x)`); argument evaluation order is unspecified, GCC passed the stale value
